# 画布任务第二轮（索引扩展、我的待办、筛选统计与动态）Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 服务端任务索引扩全画布并收录参与人（逐人子进度落表），「我的待办」按新模型改版（文件→画布分组、角色徽章、我的子进度），统计拆负责/参与两计数，新增任务动态（文件内抽屉 + 待办页跨文件动态流），筛选增加参与人维度。

**Architecture:** 数据地基=新表 `task_participant`（逐人逐列条目）+ `task_index` 加列（canvas/owner_progress/派生口径）；消费侧全部走该地基；动态=客户端写入口声明 + 服务端以连接身份盖章落 events 表（绝不信任客户端声明的操作者）；自动父派生变化由索引重建 diff 补记。

**Tech Stack:** TypeScript、Yjs、React、NestJS、TypeORM、MySQL 5.6、Vitest、Playwright。

**Spec:** `docs/superpowers/specs/2026-11-21-task-round2-design.md`

**需求方 2026-11-21 追加裁定（本计划生效）：**
- 待办页「我的子进度」选盘写入 = 我在该任务上**全部执行来源一起改**（各人员列条目 + 我是负责人时的 ownerProgress），与「展示取最高值」口径一致。
- 子进度变更**记动态**，归 `task_progress` 事件类型（payload 标明 sub 范围与对象，文案两处实现区分）。
- 按 SDD 惯例先行本计划文档，逐任务实现+独立评审。

## Global Constraints

- 所有 Yjs 写入经 `@gmind/core`（服务端同样走操作 API）；校验与 diff 在事务外，事务内不抛错。
- MySQL 5.6：无 JSON/CTE/窗口函数；payload 用 text+LIKE；索引键 ≤191；实体列显式 snake_case。
- tsx 无 DI 元数据：类注入显式 `@Inject(Token)`；新实体/迁移显式注册（目录守卫测试兜底）。
- testid 契约：新 UI 元素全部 `data-testid`；既有 testid 语义不变（todo-row/todo-check/todo-progress-range 等保留）。
- 动态操作者全链路取连接/服务端身份；payload 声明的 actor 一律覆盖；taskText 服务端从文档现值覆盖（不信任客户端文案）。
- 未经明确指令不提交、不推送；工作区既有未提交改动（TaskFields 等 6 文件，上一轮已交付）不混入本任务提交。
- 完成率/趋势/总进度三处同源 `taskProgressOf` 口径，不出现第二套算法。

## Review Focus

- 参与人重建逐人不丢：同节点多列同人各入一行；并发编辑两人各自落行（e2e 双账号钉住）。
- 「同一用户同一任务」在待办行/统计/动态三处只算一次：行按节点唯一；统计同人同任务 responsible 优先、只进一处；动态按事件行天然无重复。
- 有效进度（自动父）在索引、待办、统计三处同源 shared derive；索引重建 diff 只对 autoProgress 父补记事件，不双记普通节点。
- 旧索引行（canvas_id IS NULL）显示「未知画布」，文件装载触发一次重建修复；未打开文件的已知限制如实呈现。
- 旧客户端归一丢弃 participants 的已知限制登记（全员同版本部署无影响）。

- `task_index` 加列：`canvas_id char(26) NULL`、`canvas_name varchar(100) NULL`、`owner_progress int NULL`；`progress/status/done_date` 语义改存派生口径（`taskProgressOf/taskStatusOf/taskDoneDateOf`，与画布同算法）；旧行 `canvas_id IS NULL` = 旧口径，装载触发一次后台重建。
- `isExplicitTask` 放宽：人员列任一条目也算显式任务（统计任务总数变大，知情）。
- 重建范围：每画布 root 子树（先例 `allAliveNodeIds`）；`node_index` 维持首画布口径不变（范围变更不在本设计）。
- 自动父派生变化：重建前读旧行，对比 autoProgress 父新旧派生 progress/status——变化即补记 `task_progress`（新值 100 → `task_complete`）事件，操作者=文档 lastEditor（近似，登记）。
- `page()` 行新增 `canvasId/canvasName/myRole('owner'|'participant'|'both')/mySubProgress(int|null)/participants(string[])`；`mySubProgress` = MAX(我的人员列条目, 我是负责人时的 owner_progress)，都没有为 null；圈范围=负责人 ∪ 参与人；status 透传 `blocked`（修 blocked 显示成「未开始」）。
- `report()`：byOwner/byDepartment/byGroup 拆 `responsible`/`participating` 两计数（同人同任务只进一处，responsible 优先）；任务按负责人部门、参与人部门各计一次，合计可大于任务总数（知情）；完成率/趋势仍任务级。
- `patchTask` 新增 `mySubProgress: 0-100 整数`：我是负责人 → 写 ownerProgress；我有人列条目 → 逐列 `setAssigneeProgress`；两者皆有全写；两者皆无 400 两段式。写后记 `task_progress`（sub 范围）事件。
- stats（TodoStats）圈范围随扩：负责人 ∪ 参与人，节点唯一无重复。

**Interfaces:**
- 事件类型：`task_assign/task_assignee_add/task_assignee_remove/task_progress/task_status/task_complete/task_reopen`；payload `{fileId,canvasId,nodeId,taskText,actor,related[],before,after,scope?}`；`related` = 操作瞬间负责人+全体人员列成员（客户端声明，服务端校验字符串数组、去重、≤100、并入 actor）；子进度变更归 `task_progress` + `scope:{kind:'sub',user?}`。
- 客户端声明：`trackTaskWrite(doc, canvasId, nodeId, kind, write)`——写前快照/执行/写后快照，成功才发 stateless `{type:'task-event', ...}`；无 provider（离线）静默丢弃（已知限制）。
- 服务端盖章：actor=`connection.context.userId` 覆盖声明值；readOnly 连接丢弃；payload>8KB 丢弃；nodeId 必须在内存 doc 存活；taskText/canvasId 服务端从文档现值覆盖。
- `GET /api/todos/activity?limit=50`：events `type LIKE 'task\_%'` ∩ 可见文件 ∩（user_id=me OR payload 引号精确串含 me id）倒序；行形状同 ActivityListItem + nickname。
- 已知限制（如实登记）：断线期间本地编辑不产生事件；撤销/重做不留事件；事件不做同人短时合并。

- [x] Step 1：服务端 onStateless 盖章链路 + schema + e2e（伪造 actor 覆盖、readOnly 拒收、形状校验）。
- [x] Step 2：客户端 taskEvents.ts + 三组件写入口插桩 + web e2e（抽屉任务事件）。
